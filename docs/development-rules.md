# 開発規則

## 適用方針

小規模な問題生成ツールとして、読みやすさ、点数計算の正しさ、出力の互換性を優先する。規則は今後追加・変更するコードに適用し、既存の命名や巨大メソッドを一括変更する理由にはしない。

ユーザーから指定された仕様を優先する。仕様と実装が食い違う場合は、観測した動作と期待する動作を分けて記録する。麻雀一般のルールや別プロジェクトの挙動を、そのままこのツールの仕様にしない。

## C# とファイル構成

- .NET Framework 4.8 と従来型 `.csproj` を維持する。言語バージョンと実行環境は別なので、既存のビルド環境で使える構文・API を選ぶ。SDK 形式や新しい .NET への移行は独立した変更にする。
- 新しい型・メソッド・プロパティ・定数は `PascalCase`、引数・ローカル変数・非公開フィールドは `camelCase` とする。真偽値は `isTsumo`、`hasOpenMeld` のように意味が分かる名前にする。
- 牌の種類は `tileType`、物理的な牌 ID は `tileId`、役番号は `yakuId` のように区別する。`int` が同じでも意味の異なる数値を流用しない。
- インデントは空白 4 個、波括弧は改行して配置する。`var` は右辺から型が明らかな場合に使用できる。コメントは処理の言い換えより、制約・理由・麻雀上の条件を書く。
- 新しい主要な型を分離する場合は原則として型名とファイル名を合わせる。既存の `Program`、`TileUtilities`、`HandEvaluator` 等の改名は参照元も含めて別途判断する。
- `.cs` の追加・移動・削除は `.csproj` の `Compile Include` と同じ変更で行う。名前空間、アクセス修飾子、呼び出し名までビルドで確認する。
- ソース・文書の新規ファイルは UTF-8 とする。既存ファイルの BOM・改行を目的なく一括変換しない。生成する解答ファイルの Shift_JIS とは区別する。

## 責務とデータの扱い

- 起動・入力・ファイル出力と、手牌生成・役判定・点数計算を区別する。分離が必要な部分から小さく切り出し、単純な処理はメソッドのままでよい。
- 判定・計算の新規処理は可能な範囲で引数と戻り値だけで完結させる。計算の途中でコンソール入力やファイル出力を行わない。
- 同じ意味の牌変換、面子種別判定、役の定義を別々に追加しない。既存の共通処理を探し、共通化する場合は利用側も切り替える。
- 新しい API の結果が複数の値から成る場合は、小さな名前付きの型を検討する。既存の配列・`out` API を一括で置換する必要はない。
- 入力配列を変更するか、その参照を保持するかを明確にする。読み取り用の計算は入力を変更しない設計を優先する。保持する控えが必要ならコピーの深さを決める。
- 配列の要素変更だけのために `ref` を追加しない。配列そのものを差し替える契約かを区別する。空きを表す `0` と有効な牌種を混ぜない。
- 役番号・牌種・面子種別は互換性のある値として扱う。列挙型へ整理する場合も数値対応を維持し、境界の変換を一か所で定義する。

## 乱数と資源管理

- 一回の生成に使用する乱数源を統一する。新しい生成部品には同じ `Random` を引数またはコンストラクターで渡し、内部で時刻由来の乱数を作らない。
- リファクタリングでは乱数の呼び出し順・回数・抽選範囲も互換性に含める。固定シードの結果を変更する場合は仕様変更として説明する。
- 入力の解析では `TryParse` 等で失敗を扱い、広い `catch` で計算・I/O の失敗を黙殺しない。EOF と不正な文字列は別の状態として扱う。既存の再入力動作を変える際は仕様も更新する。
- 新しく触るストリームは `using (...)` 等で例外時にも解放する。ファイルの保存先・上書き・文字コードを明示する。
- 実行検証は専用の出力ディレクトリで行い、利用者の `question.txt` 等を上書きしない。失敗途中のファイルを成功結果として報告しない。

## 検証の基準

現時点で自動テスト専用プロジェクトはなく、[CI](ci.md) がビルド済みアプリに対する採点・牌変換の最小限の回帰検査を行う。以下は今後の変更で行う検証の基準であり、全項目を実施済みという意味ではない。

| 変更対象 | 必要な確認 |
| --- | --- |
| 文書・コメントのみ | 内容と実装の整合、リンク、差分 |
| 改名・ファイル分割 | ビルド、全参照、`Main` からの実行経路。生成経路に触れたら固定シード比較 |
| 牌変換・生成 | 境界の牌種、4 枚制約、槓を含む枚数、特殊形、固定シード |
| 役・符・点数 | 具体的な手牌と独立した期待値、親子・ツモロン、門前副露、関連する上限境界 |
| 入力・ファイル出力 | 正常値・不正値・境界値、両表示形式、3 ファイルの対応と文字コード |

1. コード変更では `msbuild MahjongScoreTrainer.sln /t:Build /p:Configuration=Debug` を実行する。プロジェクト設定を変更した場合は Release も確認する。
2. 不具合修正は、可能なら修正前に失敗し修正後に成功する最小の入力例を残す。テスト導入は対象に必要な小さな構成とし、文書変更だけのために基盤を追加しない。
3. 採点の期待値を検査対象と同じ計算式のコピーで作らない。符・飜・支払額を具体値で指定し、根拠を記録する。旧実装との一致だけでは旧実装の正しさを証明できない。
4. 共通化では関数単体だけでなく、実際の呼び出し元に値が届くことを検証する。識別子の文字列検索は補助であり、実行検証の代用にしない。
5. 重要な回帰テストは、固定値への置換や呼び出しの切断を検出するか確認する。一時的な破壊変更を使う場合は隔離して行い、必ず復元して再検証する。全変更で破壊検証を必須とはしない。
6. 同じコード・実行環境・問題数・シード・表示形式で比較する。異なる .NET バージョン間の乱数列一致を前提にしない。
7. ビルド成功、実行成功、採点の正しさを別々に報告する。環境による失敗の原因は、確認した事実と仮説を分ける。

## 小さな仕様変更の書き方

機能の変更時は [仕様書](specification.md) の該当箇所を更新する。規模が大きければ `docs/` に個別文書を追加する。次の項目を短く記載すればよく、専用の進捗管理システムは必要ない。

- 利用者が行う操作と期待結果。
- 入力、既定値、出力、不正入力・失敗時の扱い。
- 既存仕様との差、固定シードや出力形式への影響。
- 具体的な受け入れ例と検証方法。
- 未決定事項と未検証事項。
