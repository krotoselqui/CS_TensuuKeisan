# 今回のリファクタリング記録

対象コミット: `83ab017`（Main の処理分離）、`e77f400`（牌操作の共通化）
確認日: 2026-09-11

## 変更前の課題

`Program.cs` に、タイトル表示、入力、乱数設定、役の重み付き抽選、手牌生成、4 条件の採点、役別集計、3 ファイルへの保存、進捗表示、終了待ちが集中していた。役生成と採点の処理も同じファイルにあり、入力やカーソル操作を含むため、問題生成だけを自動検証しにくかった。

牌の色・数字・幺九牌判定は `Program` と `HandEvaluator` がそれぞれ持ち、`HandEvaluator` は `TileUtilities` のインスタンスを作って呼び出していた。役の番号、重み、和了条件の表示名も複数の配列に分散していた。

## Main の整理

`Main` は次の起動手順を担当するようになった。

```text
タイトル表示
  → 設定入力
  → 乱数の準備
  → Shift_JIS の3ファイルを開く
  → 問題生成と採点
  → ファイルを閉じる
  → 役別集計を表示
  → 終了キーを待つ
```

`GenerationOptions` は問題数・シード・表示形式を保持し、生成前に範囲を検査する。`ReadOptions` は `TryParse` で不正入力を再試行する。`ConsoleProgress` はカーソル位置と進捗バーだけを担当する。

`GenerateProblems` はコンソール入力を行わず、設定、乱数源、3 個の `TextWriter`、任意の進捗通知を受け取る。1 問について役を抽選し、既存の `makeYaku` で手牌を作り、同じ手牌を親ツモ・親ロン・子ツモ・子ロンの4条件で採点してから出力する。

役の重みは `YakuWeight`、和了条件は `WinningCondition`、判定結果は `EvaluatedAnswer` にまとめた。`FormatPayment` と `FormatDetails` が表示用文字列を作るため、解答と役別集計が同じ判定結果を参照する。

既存の `makeYaku`、面子生成、`HandEvaluator` の採点アルゴリズムはこの段階では移動せず、生成処理の動作を比較できる状態を保った。生成中だけ旧来の静的な乱数・表示モードを差し替え、`finally` で元の値へ戻す。`GenerateProblems` に渡された writer は借用扱いで閉じず、`Main` が開いた writer は `using` で閉じる。

## 牌操作の共通化

`TileUtilities` をインスタンスクラスから静的クラスへ変更し、次の3メソッドに責務を限定した。

| メソッド | 契約 |
| --- | --- |
| `GetColor(tileType)` | 牌種1～34を萬子・筒子・索子・字牌の0～3へ変換。不正値は-1 |
| `GetNumber(tileType)` | 牌種1～34を各色の1～9へ変換。不正値は-1 |
| `IsTerminalOrHonor(tileType)` | 字牌、または数牌の1・9なら真 |

`Program` の重複していた色・数字メソッドを削除し、`HandEvaluator` の全呼び出しをこの共通処理へ切り替えた。牌種の番号、136枚の物理牌IDからの変換、表示テーブル、役番号は変更していない。

## 検証

比較基準は整理前の `50eb05d` から Windows / .NET Framework 4.8 上で作成した。シード `0` と `12345`、表示形式 `0` と `1`、各20問について、`question.txt`、`answer.txt`、`answer_yaku.txt`、コンソール出力を保存している。

CI の `Test-Generation.ps1` は、現在のソースを検査用の一時実行ファイルへコンパイルし、次を確認する。

- 整理前の4組の出力バイト列と現在の Main の一致。
- 同じプロセスでの再実行時に集計・乱数・表示設定が意図せず残らないこと。
- 進捗通知が各問題で順番どおり呼ばれること。
- 不正入力、範囲外、整数オーバーフローが再入力になること。
- 生成本体へ渡した writer を閉じないこと。
- 出力例外が握りつぶされず、静的状態が復元されること。
- Main が所有するファイルが、後続処理を妨げず解放されること。

Debug／Release の両構成で、採点7ケース、牌変換6ケース、生成・入力・例外検査142件が成功した。ソース登録と文書リンクの検査も成功した。これは生成・採点アルゴリズムが麻雀ルール上完全に正しいことを証明するものではなく、整理による既存出力の変化を検出する回帰検査である。

## 面子生成の段階的な抽出

今回の追加変更では、面子生成のうち順子・刻子生成を `MeldGenerator.MakeRandomShuntsu` / `MeldGenerator.MakeRandomKotsu` へ移した。`Program` から呼び出しを切り替え、従来の共有乱数源 `Program.r` と残り牌配列をそのまま使うことで、乱数の呼び出し順と固定シード時の出力を維持している。新しいソースは `.csproj` に明示登録した。

抽出後に Debug / Release のビルド、採点回帰、生成回帰、リポジトリ検査を実行し、既存の 7 採点ケース、6 牌変換ケース、142 生成アサーションを通過させた。槓子・雀頭生成は次の抽出単位として残している。

## 残る課題

- `makeYaku` と槓子・雀頭生成は、まだ `Program.cs` に残っている。
- `HandEvaluator.cs` には役名・牌表示テーブルが残っており、定義の一元化は未完了である。
- `YakuDefinition` は存在するが、役の抽選設定・生成処理・判定処理を一つの契約へ統合していない。
- 役生成の全分岐、役満、特殊形、副露率の独立した期待値検査は、固定出力比較以上には増やしていない。
- 静的な `Program.r` と `PaiDisp_Mode` を完全に廃止するには、`makeYaku` 以下へ乱数源と表示設定を引数で渡す段階が必要である。

次は、面子生成を一つずつ抽出し、同じ乱数源・残り牌枚数・面子種別を渡す契約を固定する。その後、役別生成を一役ずつ移し、全抽選対象が新しい実行経路へ接続されていることを回帰検査で確認する。採点アルゴリズムの修正や生成分布の変更は、抽出とは別の変更として扱う。
