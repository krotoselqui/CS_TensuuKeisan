# 今回のリファクタリング記録

対象コミット: `83ab017`（Main の処理分離）、`e77f400`（牌操作の共通化）
確認日: 2026-09-11

## 変更前の課題

`Program.cs` に、タイトル表示、入力、乱数設定、役の重み付き抽選、手牌生成、4 条件の採点、役別集計、3 ファイルへの保存、進捗表示、終了待ちが集中していた。役生成と採点の処理も同じファイルにあり、入力やカーソル操作を含むため、問題生成だけを自動検証しにくかった。

牌の色・数字・幺九牌判定は `Program` と `HandEvaluator` がそれぞれ持ち、`HandEvaluator` は `TileUtilities` のインスタンスを作って呼び出していた。役の番号、重み、和了条件の表示名も複数の配列に分散していた。

## Main の整理

`Main` は次の起動手順を担当するようになった。

```text
タイトル表示
  → 設定入力
  → 乱数の準備
  → Shift_JIS の3ファイルを開く
  → 問題生成と採点
  → ファイルを閉じる
  → 役別集計を表示
  → 終了キーを待つ
```

`GenerationOptions` は問題数・シード・表示形式を保持し、生成前に範囲を検査する。`ReadOptions` は `TryParse` で不正入力を再試行する。`ConsoleProgress` はカーソル位置と進捗バーだけを担当する。

`GenerateProblems` はコンソール入力を行わず、設定、乱数源、3 個の `TextWriter`、任意の進捗通知を受け取る。1 問について役を抽選し、既存の `makeYaku` で手牌を作り、同じ手牌を親ツモ・親ロン・子ツモ・子ロンの4条件で採点してから出力する。

役の重みは `YakuWeight`、和了条件は `WinningCondition`、判定結果は `EvaluatedAnswer` にまとめた。`FormatPayment` と `FormatDetails` が表示用文字列を作るため、解答と役別集計が同じ判定結果を参照する。

既存の `makeYaku`、面子生成、`HandEvaluator` の採点アルゴリズムはこの段階では移動せず、生成処理の動作を比較できる状態を保った。生成中だけ旧来の静的な乱数・表示モードを差し替え、`finally` で元の値へ戻す。`GenerateProblems` に渡された writer は借用扱いで閉じず、`Main` が開いた writer は `using` で閉じる。

## 牌操作の共通化

`TileUtilities` をインスタンスクラスから静的クラスへ変更し、次の3メソッドに責務を限定した。

| メソッド | 契約 |
| --- | --- |
| `GetColor(tileType)` | 牌種1～34を萬子・筒子・索子・字牌の0～3へ変換。不正値は-1 |
| `GetNumber(tileType)` | 牌種1～34を各色の1～9へ変換。不正値は-1 |
| `IsTerminalOrHonor(tileType)` | 字牌、または数牌の1・9なら真 |

`Program` の重複していた色・数字メソッドを削除し、`HandEvaluator` の全呼び出しをこの共通処理へ切り替えた。牌種の番号、136枚の物理牌IDからの変換、表示テーブル、役番号は変更していない。

## 検証

比較基準は整理前の `50eb05d` から Windows / .NET Framework 4.8 上で作成した。シード `0` と `12345`、表示形式 `0` と `1`、各20問について、`question.txt`、`answer.txt`、`answer_yaku.txt`、コンソール出力を保存している。

CI の `Test-Generation.ps1` は、現在のソースを検査用の一時実行ファイルへコンパイルし、次を確認する。

- 整理前の4組の出力バイト列と現在の Main の一致。
- 同じプロセスでの再実行時に集計・乱数・表示設定が意図せず残らないこと。
- 進捗通知が各問題で順番どおり呼ばれること。
- 不正入力、範囲外、整数オーバーフローが再入力になること。
- 生成本体へ渡した writer を閉じないこと。
- 出力例外が握りつぶされず、静的状態が復元されること。

## 面子生成の段階的な抽出

今回の追加変更では、面子生成の4単位すべてを `MeldGenerator.MakeRandomShuntsu` / `MakeRandomKotsu` / `MakeRandomKantsu` / `MakeRandomAtama` へ移した。`Program` から呼び出しを切り替え、従来の共有乱数源 `Program.r` と残り牌配列をそのまま使うことで、乱数の呼び出し順と固定シード時の出力を維持している。新しいソースは `.csproj` に明示登録した。

抽出後に Debug / Release のビルド、採点回帰、生成回帰、リポジトリ検査を実行し、既存の 7 採点ケース、6 牌変換ケース、142 生成アサーションを通過させた。面子生成の抽出は完了し、次は役別生成の分離へ進む。

## 役抽選の分離

役番号と重み付き抽選を `YakuSelector` に移し、`Program` は `YakuSelector.Entries` と `YakuSelector.Select` を利用する構成へ切り替えた。役番号、重み、抽選範囲、`Random.Next` の呼び出し順は変更していないため、固定シードの問題生成結果を維持できる。役ごとの手牌生成本体 `makeYaku` はこの段階では移動していない。

この変更後も Debug / Release のビルド、採点回帰、生成回帰、リポジトリ検査を実行し、7 採点ケース、6 牌変換ケース、142 生成アサーションを通過させた。

## 特殊形生成の分離

`makeYaku` の七対子、九蓮宝燈系、国士無双系の分岐を `SpecialHandGenerator.Generate` へ移した。残り牌、手牌、待ち牌を引数で受け取り、既存の共有乱数源 `Program.r` と面子生成メソッドを使うため、特殊形の牌構成、待ち牌の選択、ソート前の配列内容を維持している。通常形の役別分岐と、ソート・副露・出力の後処理は `Program` に残している。

抽出後も Debug / Release のビルド、採点回帰、生成回帰、リポジトリ検査を通過した。次は通常形の役別分岐を小さなグループに分けて抽出する。

## 通常形の役別生成（大三元）

大三元の面子生成分岐を `YakuMeldGenerator.GenerateDaisangen` へ移した。三元牌の刻子・槓子、残り1面子、雀頭、待ち牌の決定を引数で受けた配列へ反映し、既存の `retOne` と同じ確率になる補助処理を保持している。`makeYaku` の後続にあるソート、副露変換、文字列出力は変更していない。

抽出後も Debug / Release のビルド、採点回帰、生成回帰、リポジトリ検査を通過した。次は四暗刻など、役の成立条件が面子種別に直接対応する分岐を同じ方法で分離する。

四暗刻の生成分岐も `YakuMeldGenerator.GenerateSuuankou` へ移した。4つの暗刻・暗槓、雀頭、待ち牌を専用メソッドで生成し、`retOne(10)` と同じ槓選択確率、面子種別、後続の共通処理を維持している。抽出後も Debug / Release の全回帰検査を通過した。

続いて四暗刻単騎を `YakuMeldGenerator.GenerateSuuankouTanki` へ移した。4つの暗刻・暗槓を同じ確率で生成し、雀頭そのものを待ち牌に設定する元の仕様を維持している。Debug / Release の全回帰検査とリポジトリ検査を通過した。

字一色の生成分岐を `YakuMeldGenerator.GenerateTsuiisou` へ移した。字牌だけを対象に4面子と雀頭を生成し、暗槓・暗刻の選択確率、副露率、待ち牌の決定を維持している。抽出後も Debug / Release の全回帰検査を通過した。

緑一色の生成分岐を `YakuMeldGenerator.GenerateRyuuiisou` へ移した。發の刻子・槓子、緑一色の順子または刻子、索子の追加面子と雀頭を生成し、各抽選率、副露率、待ち牌の決定を維持している。抽出後も Debug / Release の全回帰検査を通過した。

清老頭の生成分岐を `YakuMeldGenerator.GenerateChinroutou` へ移した。1・9牌だけで4面子と雀頭を構成し、刻子・槓子の抽選、副露率、待ち牌の決定を維持している。抽出後も Debug / Release の全回帰検査を通過した。

大四喜の生成分岐を `YakuMeldGenerator.GenerateDaisuushi` へ移した。東南西北の4面子を固定順で生成し、刻子・槓子の選択、副露率、雀頭と待ち牌の決定を維持している。抽出後も Debug / Release の全回帰検査を通過した。

小四喜の生成分岐を `YakuMeldGenerator.GenerateShousuushi` へ移した。雀頭にする風牌の抽選、残り3風の固定順、追加面子の抽選、副露率、待ち牌の決定を維持している。抽出後も Debug / Release の全回帰検査を通過した。

四槓子の生成分岐を `YakuMeldGenerator.GenerateSuukantsu` へ移した。4つの槓子と雀頭を生成し、従来存在した未使用の乱数取得も含めて乱数呼び出し順を維持している。抽出後も Debug / Release の全回帰検査を通過した。

面子生成で重複していた `retOne` を `RandomSelection.RetOne` に共通化した。`Program` と `YakuMeldGenerator` の両方が同じ `Program.r` を使うため、負数時の扱いと乱数呼び出し結果を保ったまま補助処理を一か所で管理できる。

## 残る課題

- `makeYaku` と役別生成は、まだ `Program.cs` に残っている。
- `HandEvaluator.cs` には役名・牌表示テーブルが残っており、定義の一元化は未完了である。
- `YakuDefinition` は存在するが、役の抽選設定・生成処理・判定処理を一つの契約へ統合していない。
- 役生成の全分岐、役満、特殊形、副露率の独立した期待値検査は、固定出力比較以上には増やしていない。
- 静的な `Program.r` と `PaiDisp_Mode` を完全に廃止するには、`makeYaku` 以下へ乱数源と表示設定を引数で渡す段階が必要である。

次は、`makeYaku` の役別分岐を一役ずつ移し、全抽選対象が新しい実行経路へ接続されていることを回帰検査で確認する。採点アルゴリズムの修正や生成分布の変更は、抽出とは別の変更として扱う。
