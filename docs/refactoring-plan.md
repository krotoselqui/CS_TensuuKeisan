# リファクタリング方針

## 目的と維持する仕様

問題生成と点数計算の処理を読みやすくし、変更時に壊れた箇所を特定できる状態にする。現行の C# / .NET Framework 4.8、従来型ソリューション、入力順、出力ファイル・文字コード、牌種・役番号・面子種別を維持する。

一度に大きな `Program.cs` を置換せず、呼び出し元の切り替えと検証まで含む小さな単位で進める。名前の整理、コードの移動、採点の修正、生成分布の変更を区別して検証する。CI の基礎検査に加え、プロジェクト・型名の整理とデータ型の同名ファイルへの分離は実施済み。以下は処理の責務を整理する今後の計画である。

## 段階と完了条件

Main を先に整理する依頼により、段階 5 のうち起動・入力・抽選・4 条件採点・解答整形・進捗を分離した。段階 1 の検証も、シード 0 / 12345、形式 0 / 1、各 20 問の旧 Main 出力と集計を基準に追加した。続いて段階 2 として、牌の色・数字・幺九牌判定を `TileUtilities` に一本化し、段階 3 の単位として順子・刻子・槓子生成を `MeldGenerator` へ抽出した。雀頭、`makeYaku`、採点内部は未変更である。

Main 整理では、まずタイトル・集計表示を抽出してビルドを確認し、次に設定と進捗、対応する役・条件のデータ、生成と出力のメソッドを分離した。最後に Main からの経路と直接生成の両方を基準出力と比較した。全役・特殊形の網羅的な回帰検査や、生成器の静的状態の解消まで完了したという意味ではない。

| 段階 | 変更 | 完了条件 |
| --- | --- | --- |
| 0. 基準を作る | 今回の CI で両構成のビルド、牌変換、点数の具体例を自動確認する | ローカル検査成功。push 後は GitHub で結果確認 |
| 1. 生成・採点の回帰を増やす | 固定手牌の役・符と、固定シードの生成結果を現行コードから記録する。非公開メソッドへの最小限のテスト用接続を使える | 通常形・七対子・国士・九蓮・副露・槓、親子ツモロンの代表例が検証できる。既存の不具合は別に記録 |
| 2. 共通の牌操作を整理する | 牌種の色・数字・幺九牌判定を `TileUtilities` の静的メソッドへ集約する。表示テーブルや役定義は別の小変更で整理 | 完了。`Program` と `HandEvaluator` の全参照を切り替え、重複実装を削除。数値対応、表示、固定シード結果を維持 |
| 3. 面子生成を抽出する | 雀頭・順子・刻子・槓子を順に移す。同じ `Random` と残り枚数を渡す。順子・刻子・槓子生成は `MeldGenerator` へ抽出済み | 乱数の呼び出し順を維持。牌の 4 枚制約、槓の枚数、固定シード比較が成功 |
| 4. 役別生成を抽出する | まず平和など一つの役から移し、その都度旧呼び出しを置換する。特殊形は独立した単位で扱う | 全抽選対象が生成経路に接続される。副露率・役の重み・待ち選択が従来と一致 |
| 5. 問題生成と入出力を分ける | 問題1件の生成・4条件の採点をコンソールから分離し、出力処理をまとめる。`Main` は入力・起動・進捗・終了を担当 | `Main` が新処理を実際に使う。両表示形式、3 ファイル、固定シードの比較を CI に追加 |
| 6. 採点内部を整理する | ファイル分離済みの `WinningHandData`、`HandDecomposition`、`ScoreResult` の契約を整理し、役判定と符・点数計算の境界を明確にする | 同点候補を含む結果の互換性、入力配列の非破壊、親子ツモロンと役満の回帰確認 |

段階ごとにビルドできる状態を保ち、各段階をさらに小さなコミットへ分ける。`.csproj` 登録、メソッド名、アクセス修飾子、起動経路、テスト側の接続を同時に確認する。

## 回帰検証で守ること

- 固定シードの出力は、同じ .NET 環境で変更前の基準と比較する。「変更後を2回動かして一致する」だけでは従来動作の維持を証明できない。
- 乱数消費は処理の一部として扱う。表示用の副露位置の抽選を移すだけでも、その後の問題が変わる可能性がある。
- 基準出力は実行環境・シード・問題数・形式と一緒に保存する。現行の出力記録と、独立に正しさを確認した採点の期待値を区別する。
- 抽選に出にくい役満や重み 0 の四槓子は、乱数の大量試行で代用せず役指定または固定手牌で検証する。
- 同じ牌配列を 4 条件に使うため、判定順を変えても結果が壊れないか、呼び出し前後の配列も確認する。
- 旧処理を残して比較する場合は一時的なテスト資材に限定し、本番の二重実装を恒久化しない。

## 到達させたい責務

将来の構成は次の責務を目安とする。すべてを別クラスにする必要はない。

```text
Program: 入力、進捗、終了
  -> 問題生成: 抽選、手牌生成、4 条件の採点
       -> 役別生成 -> 面子生成（同じ乱数源を共有）
       -> 役・符・点数の判定
  -> 出力: 問題、点数解答、役の詳細
共通: 牌操作、役と表示の定義
```

DI コンテナ、汎用リポジトリ層、プラグイン方式は導入しない。小さな型、メソッド、明示的な引数で十分な範囲を保つ。

## リファクタリングと分ける変更

EOF 時の終了、例外時のファイル解放・部分出力の扱い、既存の採点不具合、生成の再試行上限は機能の改善・不具合修正として別に行う。再現例、期待結果、仕様の差を示す。単なる移動の途中で見つけた問題を、比較基準と一緒に黙って書き換えない。

.NET の更新、メソッドやフィールドの全面的な英語命名化、出力ファイル形式の UTF-8 化は本計画の前提にはしない。
